# v0.6.0 compression and transfer evidence

These are deterministic synthetic fixtures measured locally with Node 24.21.0, real ClamAV, temporary filesystem objects and isolated MongoDB databases. They are not customer averages, production internet benchmarks or terabyte tests. Product measurements use runtime source commit `8929b5e`; the retained v0.5.0 image is `sha256:64ce6e5c6fe3389cd1dc92cc5a998e4c5d02f105af3d1d6e20aec7beca6d393f`. Baseline commits `dc911b5` and merge `e8cf65e` have identical trees. All recorded originals were restored and verified by SHA-256.

**Best tested settings meet 75% on 5/8 nonempty fixtures:** documents 1/1 (plus one empty N/A), structured data 1/2, developer 1/1, images 0/1, media 1/1, archives 1/2. The gzip fixture is unusually redundant even after its first encoding; it is not evidence that ordinary compressed archives shrink similarly. Custom STP1 meets 75% on 0/8 general nonempty fixtures. On the separate, deliberately correlated random-walk probe, STP1 produces 34,174 bytes from 262,144 (86.9637%), versus 61,213 for the best tested established setting, Brotli 11. This specialized win does not establish general superiority.

No real PDF/DOCX/XLSX, JPEG/RAW, MP3/MP4, medical, legal or customer datasets were supplied. Category support does not validate their ratios. No holdout was removed or tuned away.

## End-to-end transfer time

WAN application-stream shaping models 10 Mbit/s upload, 50 Mbit/s download and an 80 ms per-request delay; LAN uses 1 Gbit/s and 2 ms. This is not a TCP round-trip/congestion simulation. Counts cover file HTTP body bytes, excluding API metadata, headers and TCP/TLS overhead. The Node client uses gzip level 1; browser CPU and actual next-chunk overlap are not measured here. Timings include original verification/restore. Each single-client case has five repetitions; four-client cases have five batches / twenty observations. RSS is process-wide and includes prior work; no isolated codec-memory claim is made.

The combined product comparison changes wire encoding, storage selection and output representation together. It cannot attribute the entire speedup to the custom codec or to one component.

**Decision:** the WAN compressible cases exceed the 20% improvement goal, but the tiny gzip case and concurrent LAN cases exceed the 5% regression gate. Retain legacy raw/auto quick-send defaults. New compression is an explicit client choice. Neither the general ratio target nor universal speed improvement is achieved; production promotion remains conditional on representative corpus, device, network, inspection and actual-size trials. Do not use a useful workflow as evidence that these acceptance gaps disappeared.

## Bounded comparisons

The fixed codec grid is original control, Brotli 3/5/11, Zstandard 3/9, STP1 and gzip 6. Three five-run single-variable WAN checks isolate raw upload, original download, and smallest storage mode. No search was run on held-out content; no decoder, hash or scanner requirement was relaxed. Predictor candidates are fixed portable strides; sampling and one-next-chunk preparation remain fixed, not claimed as optimized on target browsers. Further tuning is deferred to real client evidence rather than adapting to these synthetic holdouts.

Reproduce with `scripts/benchmark-codecs.cjs` and `scripts/benchmark-transfers.cjs`; exact options are retained in each JSON result. Use explicit source/image identity, five repetitions and isolated databases as described in [COMPRESSION.md](../COMPRESSION.md).
